# 구현부터 Steam 배포까지

작성 기준: 2026-10-01  
프로젝트: `practice_puzzle_game`  
구조와 파일 역할: [TREE.md](TREE.md)

이 문서는 앞으로 진행할 작업 순서다. **0단계만 완료**, 나머지는 계획이며 실제 완료한 뒤 상태를 갱신한다. 각 단계의 완료 기준을 통과하면 다음 단계로 간다. Steam 등록·상점 준비는 대기 기간이 있으므로 게임 개발과 병행한다.

## 개발 기준과 첫 출시 범위

| 항목 | 기준 |
| --- | --- |
| 장르 | 같은 종류의 블록 3개 이상을 맞추는 2D 매치3 퍼즐 |
| 개발 | 1인 개발, C#, Unity Universal 2D |
| 에디터 | 설치 확인 버전 Unity 6.3 LTS `6000.3.25f1` |
| 버전 운영 | 정식 LTS와 호환 패키지 사용. 업데이트 시 별도 검증 후 Windows·Mac 버전을 동일하게 맞춤 |
| 도구 | Unity Personal, VS Code, Git 중심. 유료 에셋·플러그인을 필수로 두지 않음 |
| 플랫폼 | Windows 11 x64, macOS Apple Silicon부터 개발·테스트 |
| 판매 | Steam 일회 구매형, 오프라인 1인 플레이 |
| 저장 | 로컬 진행도·최고 기록·설정. 서버와 SQL 데이터베이스는 사용하지 않음 |
| 첫 조작 | 마우스 클릭으로 두 칸 선택, 이후 드래그와 트랙패드 대응 |
| 화면 | 가로형 PC 화면, 기본 16:9 및 Mac의 16:10 대응 |

**초기 설계안:** 8×8 보드, 일반 블록 6종, 이동수 제한, 점수·색상 수집·장애물 제거 목표. 먼저 1개 스테이지를 완성하고, 튜토리얼 5개 → 테스트용 10개 → 첫 출시 30개를 목표로 확장한다. 숫자·테마·정식 게임명·가격은 플레이 테스트 후 확정한다.

특수 블록은 줄 제거·주변 폭발·색 제거의 3종, 장애물은 바닥형 1종부터 시작한다. 광고, 하트 충전, 인앱 결제, 멀티플레이, 모바일, 무한 스테이지, 온라인 순위는 첫 출시 범위에 넣지 않는다. 매치3 규칙을 참고하되 게임명·그림·음악·UI는 자체 테마로 제작한다.

## 0. 설치와 실행 확인 — 완료

1. Unity Hub, Personal 라이선스, Unity 6.3 LTS 설치.
2. Universal 2D 프로젝트 `practice_puzzle_game` 생성.
3. VS Code 연동과 Unity 한국어 설정.
4. `SetupCheck.cs`를 오브젝트에 연결하고 성공 로그 확인.
5. 진행 기록을 [installation.md](installation.md), [integration.md](integration.md)에 정리.

**확인된 상태:** Windows에서 첫 C# 스크립트 실행 성공. Mac 설치·빌드와 게임 기능은 아직 완료 처리하지 않는다.

## 1. 프로젝트 백업과 버전 관리

1. 실행 모드를 종료하고 현재 씬을 저장한다.
2. Git 저장소와 Unity용 `.gitignore`를 만들고 현재 상태를 첫 커밋으로 남긴다.
3. `Assets`와 모든 `.meta`, `Packages`, `ProjectSettings`, `docs`를 추적한다.
4. `Library`, `Temp`, `Logs`, `UserSettings`, `Builds`, IDE 자동 생성 파일은 제외한다.
5. Asset Serialization은 Force Text, Version Control은 Visible Meta Files를 확인한다.
6. 원격 백업을 사용할 경우 비공개 저장소를 연결한다. 대형 원본 파일은 크기에 따라 Git LFS 또는 별도 백업을 결정한다.
7. Windows와 Mac에서 같은 커밋과 에디터 패치를 사용한다. 한 장치의 작업을 커밋·전송한 뒤 다른 장치에서 받는다.

**완료 기준:** 새 위치에 소스를 복원해 프로젝트가 열리고, 씬·스크립트 연결이 유지된다.

## 2. 기본 구조와 개발 규칙

1. [TREE.md](TREE.md)의 1차 구조를 Unity 프로젝트 창에서 만든다. 이후 폴더는 해당 기능을 만들 때 추가한다.
2. 기존 SampleScene과 SetupCheck를 테스트용 위치로 옮기되 `.meta`와 참조를 보존한다. 별도로 빈 `Game` 씬을 만든다.
3. `Core`는 순수 C# 게임 규칙, `Runtime`은 Unity 화면·입력·설정·저장으로 분리한다.
4. Core, Runtime, EditMode 테스트용 어셈블리 정의를 만든다. Editor·PlayMode 테스트 어셈블리는 필요 단계에서 추가한다.
5. 보드 좌표는 왼쪽 아래 `(0, 0)`, 오른쪽이 x 증가, 위쪽이 y 증가로 통일한다.
6. 파일·클래스명은 영어 PascalCase, 스테이지 ID는 `level_001` 형식으로 정한다.
7. 웹 개발과 다른 Unity 기본 개념인 씬, GameObject, Component, Prefab, Inspector, MonoBehaviour, Coroutine을 작은 예제로 확인한다.

**완료 기준:** 빈 Game 씬이 열리고 컴파일 오류가 없으며 Core가 Unity 객체를 참조하지 않는다.

## 3. 두 운영체제에서 첫 실행 파일 만들기

1. Mac에 Apple Silicon용 Hub·동일 버전 Unity·VS Code를 설치하고 같은 소스를 연다.
2. `File → Build Profiles`에서 Windows와 macOS 프로필을 만든다.
3. Windows는 x64, M3 Pro 테스트용 macOS는 Apple Silicon을 선택한다.
4. 우선 기본 Mono 백엔드로 작은 실행 파일을 만든다. IL2CPP로 변경한다면 해당 플랫폼의 빌드 도구·모듈을 갖추고 다시 검증한다.
5. Windows 빌드는 Windows에서, Mac 빌드는 Mac에서 만들어 각각 실제 실행한다.
6. 빈 화면이라도 실행·창 크기 변경·종료·로그 출력을 확인한다.
7. Intel Mac 지원은 별도 검증 환경을 확보한 뒤 Universal 빌드로 확장한다.

**완료 기준:** Unity 편집기를 닫아도 두 장치에서 앱이 열린다. 기능이 늘어날 때마다 두 플랫폼 빌드를 반복한다.

Unity의 macOS 아키텍처 선택과 Windows에서 만든 Mac 앱의 실행 권한 주의사항은 [공식 빌드 문서](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/apple-mac/macos-delivery/macos-building)를 기준으로 한다.

## 4. 보드 데이터와 블록 표시

1. `GridPosition`, `PieceState`, `CellState`, `BoardState`를 만든다.
2. 셀 위치·바닥 상태와 움직이는 블록의 색·특수 종류를 분리한다.
3. 8×8 배열로 보드 상태를 만들고 디버깅용 난수 seed를 지정할 수 있게 한다.
4. 처음부터 3개가 이어지지 않도록 블록을 생성한다.
5. 최소 가로·세로 3매치 검사(`MatchFinder`)와 인접 교환 검사(`MoveFinder`)를 구현해 가능한 이동이 최소 1개 있는지 확인한다. 판정 정보는 6단계에서 확장한다.
6. 생성 재시도 횟수에 상한을 두고, 불가능한 레벨은 오류로 보고한다.
7. 임시 도형 6종과 `Piece.prefab`으로 데이터를 화면에 표시한다. 색뿐 아니라 모양으로도 구분한다.
8. 카메라와 보드 크기를 맞추고 화면 비율이 바뀌어도 보드 전체를 보여 준다.

**완료 기준:** 64개 블록이 데이터와 동일하게 표시되고, 초기 매치가 없으며 가능한 이동이 존재한다.

## 5. 블록 선택과 교환

1. 설치된 Input System으로 포인터 위치·선택·취소 입력을 받는다.
2. 화면 좌표를 보드 좌표로 변환하고 보드 밖 입력과 UI 위 입력을 무시한다.
3. 선택한 블록을 강조하고 두 번째 선택이 상하좌우 인접한지 검사한다.
4. 같은 칸·대각선·먼 칸·움직일 수 없는 칸의 교환을 막는다.
5. 인접 블록을 교환하고 애니메이션이 끝날 때까지 추가 입력을 잠근다.
6. 매치가 없으면 원래 자리로 복귀한다. 이때 이동수와 목표는 바뀌지 않는다.
7. 클릭 동작이 안정되면 드래그 방향·최소 거리·선택 취소도 추가한다.

**완료 기준:** 빠르게 연속 클릭하거나 창 밖에서 놓아도 데이터와 화면 위치가 어긋나지 않는다.

## 6. 매치 판정 확장

1. 4단계의 기본 판정을 확장해 가로·세로의 같은 색 3개 이상인 연속 구간을 모두 수집한다.
2. 전체 탐색을 끝낸 뒤 제거 좌표를 합친다. 탐색 도중 보드를 지우지 않는다.
3. 십자·T·L 모양의 겹치는 좌표를 한 번만 제거하도록 처리한다.
4. 대각선은 매치로 인정하지 않는다.
5. 3개, 4개, 5개 직선과 교차 모양을 구별할 정보를 결과에 담는다.
6. 안정된 보드에서 교환한 결과를 검사하며 임시 검사 뒤에는 상태를 정확히 되돌린다.

**완료 기준:** 고정된 테스트 보드에서 매치 위치가 예상과 정확히 일치한다.

## 7. 제거 → 낙하 → 보충 → 연쇄

1. 유효 교환에만 이동수 1을 차감하고 보드 해결 처리를 시작한다.
2. 매치 좌표를 한꺼번에 제거하고 이번 제거의 점수·수집 이벤트를 만든다.
3. 같은 열의 남은 블록을 아래부터 빈칸 없이 압축한다. 위아래 순서를 유지한다.
4. 위쪽 빈칸에 새 블록을 만들고 낙하 애니메이션을 재생한다.
5. 보충 후 매치가 있으면 제거부터 반복한다. 연쇄에는 이동수를 추가 차감하지 않는다.
6. 계산 결과에 제거·이동·생성 기록을 담아 화면이 순서대로 재생하도록 한다.
7. 전체 처리가 끝날 때까지 입력을 잠그고, 씬 종료 시 코루틴과 입력 구독을 정리한다.
8. 개발 중 비정상적으로 긴 연쇄는 seed와 보드를 기록한다. 조용히 잘못된 보드로 진행하지 않는다.

**완료 기준:** 긴 연쇄에서도 빈칸·중복 블록·중복 점수·입력 잠김이 남지 않는다.

```text
입력 대기 → 교환 → 매치 없음: 복귀 → 입력 대기
                 → 매치 있음: 이동수 1 차감
                    → 제거 → 낙하 → 보충 → 다시 매치 검사
                    → 안정화 → 목표/이동수/가능한 이동 검사
```

## 8. 한 스테이지를 끝까지 플레이

1. 점수 목표와 이동수 표시를 먼저 연결한다.
2. 색상별 수집 목표를 추가하고 목표 진행도를 제거 결과로 갱신한다.
3. 마지막 연쇄까지 끝난 뒤 목표 달성을 먼저 검사한다.
4. 목표를 달성했다면 성공, 달성하지 못했고 이동수가 0이면 실패로 처리한다.
5. 성공·실패 화면에 다시 하기·다음 스테이지·메뉴 버튼을 만든다.
6. 게임이 계속되는데 가능한 이동이 없으면 블록을 섞는다. 목표·점수·이동수는 유지한다.
7. 섞은 보드도 즉시 매치 없음·가능한 이동 있음 조건을 검사하고 재시도 상한을 둔다.
8. 일정 시간 입력이 없으면 가능한 교환 한 쌍을 힌트로 보여 준다.

**완료 기준:** 시작부터 성공·실패·재시작까지 1개 스테이지를 플레이한다. 마지막 이동으로 목표를 달성해도 성공한다.

## 9. Steam 등록과 출시 일정 준비 — 이후 개발과 병행

1. 정식 게임명 후보, 개발자 표시명, 자체 테마를 정리한다.
2. 공개할 만한 플레이 화면이 확보되면 Steamworks 등록을 진행한다.
3. 본인·은행·세금 정보와 Steam Direct 제품 등록 비용을 준비한다.
4. 상점 설명, 캡슐 이미지, 실제 플레이 스크린샷, 게임 영상, 지원 언어를 준비한다.
5. Windows·macOS의 실제 검증 범위에 맞춰 시스템 요구사항을 작성한다.
6. 콘텐츠 설문과 지역별 등급 항목을 작성한다. AI로 제작한 출시 콘텐츠가 있으면 해당 질문과 공개 기준을 확인한다.
7. 상점 심사 후 Coming Soon 페이지를 공개하고 위시리스트를 받을 수 있게 한다.
8. 출시 일정·AppID·공개한 지원 기능을 `docs/release.md`에 기록한다.

**일정 기준:** 2026-10-01 확인 시 제품 등록 비용은 US$100 기준이며 현지 통화·세금이 적용될 수 있다. 첫 출시에는 비용 결제 후 30일과 Coming Soon 공개 최소 2주가 필요하다. 실제 결제·출시 전 [Steam 등록 안내](https://partner.steamgames.com/doc/gettingstarted/onboarding)와 [비용 안내](https://partner.steamgames.com/doc/gettingstarted/appfee)를 다시 확인한다.

**완료 기준:** 등록·상점 심사·Coming Soon 공개 일정이 개발 일정과 함께 관리된다. 이 문서 작성만으로 결제나 공개를 진행하지 않는다.

## 10. 특수 블록

1. 4개 직선 매치는 해당 방향의 한 줄을 지우는 블록을 만든다.
2. T/L 매치는 주변 3×3을 지우는 블록, 5개 이상 직선은 색 제거 블록을 만든다.
3. 겹친 후보의 우선순위는 색 제거 → 주변 폭발 → 줄 제거로 정한다.
4. 생성 위치는 교환 도착 칸 → 다른 교환 칸 → 좌표순의 유효한 일반 블록 칸으로 결정한다.
5. 겹친 매치 그룹마다 특수 블록을 최대 1개 만들고, 새 특수 블록은 자신을 만든 제거에서 살아남게 한다.
6. 연쇄로 생긴 매치에도 같은 규칙을 적용하되 교환 칸이 없으면 좌표순으로 정한다.
7. 기존 특수 블록은 매치나 다른 특수 효과에 맞으면 발동시킨다. 효과 큐와 블록 ID로 중복 발동을 막는다.
8. 색 제거 블록과 일반 블록의 교환은 매치가 없어도 상대 색 제거로 인정한다.
9. 색 제거의 연쇄 발동처럼 상대 색이 없는 경우에는 가장 많은 일반 색을 선택하고 동률은 색 ID 순으로 정한다.
10. 색 제거 이외의 특수 블록끼리 직접 교환하면 두 효과를 각각 한 번 실행한다. 색 제거+특수는 상대 기본 색 제거와 상대 효과 1회, 색 제거+색 제거는 전체 블록 제거로 정한다.
11. 가능한 이동 검사와 힌트에도 같은 특수 교환 규칙을 적용한다. 셔플은 블록의 색·특수 종류를 보존한다.
12. 줄 제거·주변 폭발은 기본 색을 유지해 일반 매치에 참여한다. 색 제거 블록은 기본 색이 없으며 일반 3매치 판정에서 제외한다.

**완료 기준:** 모든 특수 교환·연쇄에서 이동수는 한 번만 줄고, 같은 블록이 중복 발동하지 않는다. 고유한 조합 연출·대형 합성 효과는 이후 확장으로 남긴다.

## 11. 장애물과 추가 목표

1. 첫 장애물은 블록 아래에 고정된 바닥형 `Frost`로 만든다.
2. 장애물 위의 블록이 제거되면 내구도를 1 줄인다. 낙하나 교환은 막지 않는다.
3. 같은 제거 단계에서 여러 효과가 겹쳐도 해당 칸의 내구도는 1만 줄인다.
4. 특수 블록 생성으로 살아남는 칸은 제거로 계산하지 않는다. 직접 효과가 타격한 칸의 처리는 동일한 피해 규칙으로 통일한다.
5. 바닥은 낙하·셔플로 이동하지 않으며 파괴 시 제거 목표가 갱신된다.
6. 점수·색상 수집·장애물 제거의 복합 목표는 모두 달성해야 성공한다.
7. 벽·빈 구멍·통과 금지 칸은 첫 출시 필수에서 제외한다. 추가한다면 낙하 구간·새 블록 유입 경로·가능한 이동 검사를 먼저 확장한다.

**완료 기준:** 특수 효과·연쇄·셔플 후에도 장애물 위치와 목표 수량이 정확하다.

## 12. 스테이지 데이터와 제작 도구

1. `LevelDefinition` ScriptableObject에 ID, 크기, 색 종류, 이동수, 목표, 초기 배치, 바닥 정보를 정의한다.
2. 시작 시 데이터를 복사·변환해 Core의 실행 상태를 만든다. 원본 에셋을 플레이 중 수정하지 않는다.
3. `LevelCatalog`에 스테이지 순서와 다음 레벨 연결을 보관한다. 저장에는 목록 순서 대신 고정 ID를 쓴다.
4. 중복 ID, 범위를 벗어난 칸, 잘못된 색, 0 이하 이동수, 빈 목표, 목표 수량 오류를 검사한다.
5. 고정 배치의 초기 매치·가능한 이동도 검증한다. 의도적인 튜토리얼 배치는 별도 테스트한다.
6. 처음에는 Inspector로 만들고 반복 작업이 생기면 `LevelEditorWindow`에 격자 편집·저장·검증을 추가한다.
7. 레벨 난수 seed·규칙 버전·플레이 결과를 기록해 버그를 재현한다.

**완료 기준:** C# 수정 없이 레벨을 추가하고 잘못된 설정을 플레이 전에 찾을 수 있다.

ScriptableObject는 제작 데이터에 쓰고, 사용자 진행도 저장 파일은 별도로 둔다. [Unity 공식 설명](https://docs.unity3d.com/6000.3/Documentation/Manual/class-ScriptableObject.html)

## 13. 메뉴와 게임 화면 연결

1. `Boot → MainMenu → LevelSelect → Game` 씬 흐름을 만든다.
2. Boot에서 설정·저장·데이터를 읽고 공통 서비스를 한 번만 초기화한다.
3. 메인 메뉴에 시작·설정·크레딧·종료를 만든다.
4. 스테이지 선택 화면에 잠금·해금·목표·최고 기록을 보여 준다.
5. Game에는 목표·남은 이동수·점수·일시정지 버튼을 배치한다.
6. 일시정지·결과 팝업은 Game 씬 안의 UI로 만든다.
7. 재시작·다음 레벨·메뉴 복귀를 반복해도 서비스·이벤트 구독이 중복되지 않게 한다.
8. ESC, 창 포커스 변경, 창 크기 변경, 전체 화면 전환을 확인한다.

**완료 기준:** 실행 파일에서 코드나 Inspector 조작 없이 모든 화면을 이동할 수 있다.

## 14. 로컬 저장과 복구

1. `SaveData`에 저장 형식 버전, 해금 레벨 ID, 레벨별 최고 점수·클리어 기록을 정의한다.
2. `SettingsData`에는 음량·언어·화면 모드·접근성 설정을 저장한다.
3. `Application.persistentDataPath`와 `Path.Combine`을 사용해 OS별 저장 위치를 처리한다.
4. 진행도는 `progress.json`, 장치별 설정은 `settings.json`으로 분리한다.
5. 임시 파일에 쓰고 검증한 뒤 본 파일을 교체한다. 이전 정상본 `.bak`과 오류 처리를 둔다.
6. 스테이지 완료·설정 변경 시 저장한다. 종료 이벤트에만 의존하지 않는다.
7. 파일 없음·손상·이전 버전·쓰기 실패·중복 레벨 기록을 테스트한다.
8. 저장 초기화는 확인 팝업을 거친다. 진행 중 보드 복원은 첫 버전에서 제외한다.

**완료 기준:** 앱을 종료하고 다시 열어도 진행도가 유지되며, 손상 파일은 백업 복구 또는 안내 후 초기화된다.

플랫폼마다 실제 저장 경로가 다르므로 프로젝트 폴더나 하드코딩된 드라이브 경로에 저장하지 않는다. [Unity persistentDataPath](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/application/persistentdatapath)

## 15. 그림·소리·언어·접근성

1. 임시 블록을 고유한 테마의 스프라이트로 교체하고 선택·교환·제거·낙하 연출을 다듬는다.
2. 반복 제거에 쓰는 이펙트는 필요 시 풀링하고 과한 흔들림·깜박임을 줄인다.
3. 배경음·교환·실패·매치·연쇄·클리어 효과음을 연결하고 AudioMixer에서 음량을 분리한다.
4. 효과음이 겹칠 때 최대 동시 재생 수를 정한다.
5. UI는 Canvas/uGUI와 TextMeshPro를 사용하고, 한국어 글꼴 및 글리프 누락을 확인한다.
6. 화면 문구는 문자열 키로 관리한다. 한국어부터 완성하고 영어를 추가한다.
7. 색상 외에 모양·기호를 사용하고 글자 크기·명암·이펙트 감소 옵션을 확인한다.
8. 첫 5개 레벨에서 선택·교환·목표·특수 블록·장애물을 순서대로 알려 준다.
9. 모든 외부 그림·음악·폰트의 출처·라이선스·상업 이용 조건·표기 의무를 기록하고 크레딧에 반영한다.

**완료 기준:** 설명 없이도 첫 레벨을 진행할 수 있고, 소리를 끄거나 색 구분이 어려워도 플레이할 수 있다.

## 16. 콘텐츠 제작과 난이도 조정

1. 튜토리얼 5개를 먼저 검증하고 테스트용 10개까지 확장한다.
2. 직접 플레이와 외부 테스트로 성공률·남은 이동수·소요 시간·막힌 이유를 기록한다.
3. 서로 다른 seed에서 과도하게 운에 좌우되거나 목표 달성이 불가능한 상황을 찾는다.
4. 이동수·색 개수·목표량·장애물 배치를 조정한다.
5. 재미와 제작 속도를 확인한 뒤 첫 출시 목표 30개를 확정하거나 줄인다.
6. 마지막 레벨 이후의 완료 화면과 이미 깬 레벨 재도전을 만든다.
7. 이 시점부터 출시 필수 기능을 고정하고 새 아이디어는 이후 업데이트 항목으로 분리한다.

**완료 기준:** 확정한 모든 레벨을 정상 플레이로 완료할 수 있고, 출시 분량·예상 플레이 시간·가격을 설명할 수 있다.

## 17. 자동 검사와 실제 플레이 검증

규칙 테스트는 4단계부터 기능과 함께 추가하고, 여기서는 출시 전 전체 회귀 검사를 진행한다.

| 구분 | 반드시 확인할 사례 |
| --- | --- |
| 보드 생성 | 초기 매치 없음, 가능한 이동 있음, 생성 재시도 상한 |
| 교환·판정 | 인접 규칙, 실패 복구, 대각선 제외, 교차 매치 중복 제거 |
| 해결 과정 | 낙하 순서, 연쇄, 이동수 1회 차감, 블록 ID·좌표 일치 |
| 게임 종료 | 마지막 이동 성공, 목표 미달 실패, 결과 중복 표시 방지 |
| 특수·장애물 | 우선순위, 생성 위치, 조합, 중복 발동·피해 방지, 셔플 유지 |
| 데이터·저장 | 레벨 검증, 저장 왕복, 이전 버전, 손상·쓰기 실패 복구 |
| Unity 연결 | UI 클릭이 보드로 전달되지 않음, 처리 중 입력 잠금, 씬 전환 정리 |
| 실제 플랫폼 | Windows와 M3 Pro의 입력·저장·음량·전체 화면·재실행 |
| 사용 환경 | 16:9·16:10·작은 창·고해상도 배율·한글 사용자 경로·오프라인 |
| 업데이트 | 구버전 진행도를 새 빌드에서 열고 다음 레벨 진행 |

1. EditMode는 고정 데이터와 seed로 규칙을 검사하고 PlayMode는 화면·입력 연결을 검사한다.
2. 문제 보고에는 버전, OS, 레벨 ID, seed, 재현 순서, 로그를 남긴다.
3. 출시 후보는 최소 1시간 연속 플레이하며 크래시·진행 막힘·메모리 증가를 확인한다.
4. Unity Profiler로 실제 병목을 확인한 부분만 개선한다. 목표 장치에서 안정적인 60 FPS를 목표로 한다.
5. 치명적 오류인 실행 실패·저장 유실·진행 불가를 먼저 해결한다.

**완료 기준:** 필수 검사 통과, 알려진 치명적 오류 0건, 테스트한 장치·OS·빌드 번호 기록.

## 18. 선택 기능 — Steam Cloud·업적·컨트롤러

1. 첫 출시의 기본은 로컬 저장이다. 아래 기능은 추가할 때만 상점에 표시한다.
2. Cloud가 필요하면 Auto-Cloud에 진행도 파일을 등록하고 Windows↔Mac 왕복 동기화를 검사한다.
3. Auto-Cloud의 공통 root와 OS별 Root Overrides를 연결한다. 장치별 화면 설정과 임시 파일은 제외한다.
4. 동시 실행·오프라인 저장·충돌·오래된 파일 복원 상황을 검사한다.
5. 업적은 게임 내부 Steamworks API 연동을 추가할 때 구현한다. 사용할 C# 래퍼의 유지보수·라이선스·양쪽 OS 및 아키텍처 지원을 먼저 확인한다.
6. Steam API 초기화 실패 시 오프라인 플레이가 가능한지 확인한다.
7. 컨트롤러 지원을 추가하면 보드 커서·UI 포커스·조작 안내까지 완성한다. Steam Deck·Linux 지원은 별도 범위다.

**완료 기준:** 선택하지 않은 기능 없이도 출시 가능하며, 선택한 기능은 두 플랫폼에서 검증된다.

게임 내부 Steam API 연동은 출시 필수가 아니다. [Steamworks SDK](https://partner.steamgames.com/doc/sdk) · [Steam Cloud 설정](https://partner.steamgames.com/doc/features/cloud)

## 19. 최종 플랫폼 빌드

1. Company Name, Product Name, 앱 식별자, 버전, 아이콘, 시작 씬을 확정한다. 저장 경로에 영향을 주는 이름은 이후 함부로 바꾸지 않는다.
2. Windows/macOS Build Profile의 씬 목록과 출력 경로를 확인한다.
3. Development Build·Script Debugging·디버그 메뉴·테스트 씬을 출시 빌드에서 제외한다.
4. Windows 출력은 `.exe`와 데이터 폴더·런타임 DLL을 함께 보관한다.
5. macOS 출력은 `.app` 번들과 필요한 파일을 보관한다. M3 Pro에서 ARM64 실행을 확인한다.
6. Intel 지원 시 Universal 빌드와 네이티브 플러그인 아키텍처를 확인하고 Intel 환경도 검증한다.
7. macOS 서명·공증 요구를 현재 Steamworks 지침과 지원 답변으로 확인한다. 필요 시 Developer ID 서명 → 공증 → staple 후 다시 테스트한다.
8. 서명·공증을 선택하거나 요구받는 경우 Apple 계정·인증서·비용을 출시 예산에 반영한다. Xcode 사용과 유료 개발자 프로그램 가입은 구분한다.
9. 깨끗한 장치 또는 새 사용자 환경에서 최종 빌드의 실행·저장·종료를 확인한다.
10. 같은 Git 커밋에서 만든 OS별 결과물과 버전·빌드 날짜를 기록한다.

**완료 기준:** 약속한 모든 플랫폼에서 설치·실행 가능한 출시 후보가 준비된다.

macOS 공증 관련 현재 플랫폼 문서와 과거 Valve 안내에는 표현 차이가 있으므로 출시 시점에 확인한다. ## 20. Steam 업로드와 비공개 테스트

1. Steamworks에서 Windows·macOS depot(플랫폼별 배포 파일 묶음)을 만든다.
2. OS별 실행 파일 경로와 실행 옵션, depot을 제공하는 package를 설정한다. macOS 실행 옵션은 `.app` 번들 경로를 우선 사용한다.
3. `Tools/Steam`에 AppID·DepotID·출력 경로를 담는 VDF 설정 파일을 만든다. 비밀번호는 넣지 않는다.
4. Steamworks SDK의 SteamPipe 도구로 빌드를 올린다. 업로드 도구 사용과 게임 API 연동은 별개다.
5. 암호로 보호한 beta branch에 BuildID를 지정한다.
6. 실제 Steam 클라이언트로 두 OS에서 새로 설치하고 실행한다.
7. 업데이트·재설치·파일 검증·오프라인 플레이·기존 저장 유지·선택한 Cloud 기능을 검사한다.
8. macOS 앱의 실행 권한과 Steam을 통한 설치 후 최초 실행도 확인한다.
9. 정상 BuildID와 이전 버전으로 되돌리는 절차를 기록한다.

**완료 기준:** 개발 폴더의 실행 파일이 아니라 Steam에서 받은 게임으로 전체 플레이가 가능하다.

업로드·depot·branch의 실제 설정은 [SteamPipe 공식 가이드](https://partner.steamgames.com/doc/sdk/uploading)를 따른다.

## 21. 심사와 정식 출시

1. 상점 설명·영상·가격·지원 기능·언어·시스템 요구사항이 실제 빌드와 일치하는지 최종 확인한다.
2. 출시 후보를 심사용 default branch에 지정하고 상점·빌드 체크리스트를 완료한다.
3. 빌드 심사를 요청하고 수정 요청이 오면 수정·검증·재제출한다.
4. 상점과 빌드 심사는 보통 3~5영업일이며, 각 심사에 최소 7영업일 이상의 여유를 잡는다.
5. 비용 결제 후 대기 기간, Coming Soon 기간, 승인 상태, 공개 날짜·시간을 확인한다.
6. 출시 버전 태그와 결과물을 보관하고 릴리스 노트·지원 연락처를 준비한다.
7. 실제 출시 시 Steamworks의 Release App 절차로 공개한다. 심사 승인만으로 자동 출시되지 않는다.
8. 공개 후 일반 구매자 관점의 상점·구매·설치·실행 상태를 확인한다.

**완료 기준:** Steam 상점에서 구매 가능하고 Windows·macOS용 올바른 파일이 배포된다.

심사 일정은 보장 시간이 아니므로 출시 전 다시 확인한다. [심사 안내](https://partner.steamgames.com/doc/store/review_process) · [출시 절차](https://partner.steamgames.com/doc/store/releasing)

## 22. 출시 후 수정과 유지보수

1. 사용자 문의·리뷰·재현 가능한 버그를 기록한다.
2. 실행 실패·저장 문제·진행 불가를 우선 처리한다.
3. 수정 빌드는 자동 검사 → 두 OS 실행 → Steam beta branch 검증 후 default에 반영한다.
4. 업데이트 전후 저장 호환성과 레벨 ID를 유지한다. 필요한 경우 저장 마이그레이션을 추가한다.
5. 새 버전과 이전 정상 BuildID를 기록하고 문제가 있으면 되돌린다.
6. 게임 파일 롤백만으로 저장 파일이 되돌아가지는 않으므로 구버전 저장 호환성도 확인한다.
7. 패치 노트를 공개하고 새 레벨·새 테마·선택 기능은 안정화 후 추가한다.
8. Unity LTS 지원·라이선스 조건·Steam 정책은 주요 업데이트와 출시 전에 다시 확인한다.

**완료 기준:** 사용자 저장을 유지하면서 검증한 패치를 반복 배포할 수 있다.
